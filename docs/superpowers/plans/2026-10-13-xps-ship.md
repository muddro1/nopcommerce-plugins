# Plan: `Misc.XpsShip`, an XPS Ship webhooks plugin for nopCommerce 4.90 and 4.50

> **Status (2026-10-13):** 4.90 (2.00) built and tested. The 4.50 backport was deferred at the user's request partway through the build, so every 4.50 step below is still to do.

## Context
Every XPS label today comes from a hand-entered order, and the tracking number is retyped into nopCommerce afterwards. Over the last 90 days that produced inconsistent tracking text, UPS shipments with no weight, and orders marked Complete with no shipment. Your spec (*XPS Ship Webhooks Integration: Plugin Spec*, 2026-09-24) defines a webhooks plugin to replace that. XPS pulls ready-to-ship orders, posts each label back, and the plugin creates a real nopCommerce shipment through the stock pipeline.

**The spec is the source of truth.** This plan records only the decisions made since, the gaps I found, and how the work is built in this repo. Decisions made in this session:
- **Full spec scope** in the first release.
- **Spec order-selection rules**: paid or Open Payment, Hold list, exchange release, backorder hiding, `BACKORDERED:` prefix.
- **Both nopCommerce versions.** Build **4.90 first** (the clean install you're moving to), then backport to 4.50.2 (the live store). Versions **2.00 (4.90) / 1.00 (4.50)** per the repo convention.

## Gaps and corrections to the spec (folded into the build)
1. **Voids don't reset shipping status.** I checked the admin `OrderController.DeleteShipment` in both trees (4.50.2 line ~2150, 4.90 line ~2035). It reverses booked inventory, deletes the shipment and adds a note, but never recomputes `Order.ShippingStatus`. The plugin's Void action does the same steps and then sets ShippingStatus itself:
   - *Partially shipped* if other shipped shipments remain, otherwise *Not yet shipped*;
   - updates the order and calls `IOrderProcessingService.CheckOrderStatusAsync`.

   Without this, T18 fails and the order never returns to List Orders.
2. **Admin menu location.** The spec says "under Sales", but every 4.90 plugin here uses the shared **FMS Plugins** menu. Plan: 4.90 puts the item under Sales, as the spec says, and also under FMS Plugins (a copy of `HandlingFee/.../Infrastructure/FmsPluginsMenuConsumer.cs` with the item constants changed). 4.50 uses `IAdminMenuPlugin.ManageSiteMapAsync` to add the Sales item.
3. **Migration timestamp.** It must be unique across all plugins in the repo (README rule). The taken timestamps run up to `2026/10/12 19:31:46`. Use `2026/10/13 09:14:27`, and use the same value in both version builds, because only one build is ever installed on a given store.
4. **Rate limiting, per-order lock and HTTPS detection** are in-process. They use `IMemoryCache` / a keyed `SemaphoreSlim`, and HTTPS is checked with `IWebHelper.IsCurrentConnectionSecured()` so it respects nopCommerce's forwarded-headers setting behind a proxy. This is fine for the single web server; it is noted in the Readme as a web-farm limitation.
5. **Log purge** needs a daily schedule task, `XpsShip.PurgeLog`, registered on install and removed on uninstall. The spec names `LogRetentionDays` but no mechanism.
6. **Permissions differ by version.** 4.50 uses `StandardPermissionProvider.ManageOrders`. 4.90 uses `StandardPermission.Orders.ORDERS_VIEW` for viewing and `ORDERS_CREATE_EDIT_DELETE` for actions: hold, release, void, regenerate key and save.
7. **Not in this repo:** `FMS_Reference_Notes.md`, which the spec says to update (UPS mostly, then USPS; XPS status). I couldn't find it locally, so I'll ask where it lives at the end rather than guess.
8. The open decisions in spec #7 and #8 (XPS non-200 behaviour, XPS outbound IPs) remain questions for XPS support. Until they're answered, the build uses the spec defaults: 404/422 replies, and an IP allowlist that is empty by default.

## Source structure (same files in both versions; differences listed after)
- **`XpsShipPlugin.cs`** (`BasePlugin, IMiscPlugin`, plus `IAdminMenuPlugin` on 4.50):
  - Install: settings with a random 32-character key, the spec's sender and service-map defaults, locales, and the purge task.
  - Uninstall: drops the tables, settings, locales and task.
  - Configure URL: `Admin/XpsShip/Configure`.
- **`XpsShipSettings.cs`**: every setting in the spec's table, plus `IpAllowlist`.
- **`Domain/`**: `XpsShipTrackingMap`, `XpsShipOrderFlag`, `XpsShipWebhookLog`.
- **`Data/SchemaMigration.cs`** (`[NopMigration("2026/10/13 09:14:27", ..., MigrationProcessType.Installation)]`) and **`Data/*BuilderCompatible` mapping**. All tables use the `XpsShip_` prefix and GUID/number keys only.
- **`Infrastructure/`**:
  - `RouteProvider`: `/xps/orders`, `/xps/order`, `/xps/update`, and the admin routes.
  - `NopStartup`: DI registrations.
  - the menu consumer or plugin hook.
- **`Services/`** (the endpoints call these, so most of the logic is unit-testable):
  - `XpsOrderSelector`: applies selection rules 1–7. It returns included orders plus excluded orders with a reason, which feeds the Preview. Stock checks handle combination stock, and the 9998–10000 placeholder counts as in stock.
  - `XpsOrderMapper`: maps an order to the XPS DTO per the spec's Data mapping tables. It covers the service-key map, the "Customer selected:" note, special-instruction parsing (HTML strip, PO regex, 35-character reference) and title building with the `BACKORDERED:` prefix. Decimals are written as invariant 2-place strings, 4 places for weight.
  - `XpsUpdateProcessor`: implements the Update Order flowchart steps 1–10. It returns 401, 404, 422, 200 (duplicate) or 200 (shipped). It ships via `IShipmentService` + `IOrderProcessingService.ShipAsync`. When there are multiple packages it adds a customer-visible note through `InsertOrderNoteAsync` and sends no note email.
  - `TrackingNumberParser`: split, trim, uppercase and dedupe; strip carrier text; detect the carrier from the number's format (1Z → ups, 12 or 15 digits → fedex, 92–95 prefix with 20–22 digits → usps).
  - `XpsVoidService`: the void flow, including gap #1.
  - `XpsWebhookLogger` (8 KB body cap, never logs the key) and `XpsRequestGuard`: HTTPS → 403, IP allowlist, constant-time key check, fail counter that blocks an IP for 1 hour after 30 failures in 10 minutes and writes an Error to the nopCommerce log.
  - `XpsTrackingTokenConsumer` (`IConsumer<EntityTokensAddedEvent<Shipment, Token>>`): adds `%Shipment.XpsTrackingUrl%`. The carrier comes from the tracking map, then the number's format, then the order-page URL as a fallback.
  - `PurgeWebhookLogTask` (`IScheduleTask`).
- **`Controllers/XpsWebhookController.cs`**: public, `[IgnoreAntiforgeryToken]`, runs with no customer session writes, and sends `X-Robots-Tag: noindex`. Returns 503 when disabled.
- **`Controllers/XpsShipAdminController.cs`** + Models + Views: tabs for:
  - settings, with the three URLs, copy buttons and Regenerate key;
  - Preview, showing included JSON and excluded orders with reasons;
  - Hold and exchange release, with search by order number and a reason;
  - Labels, the tracking-map rows with Void;
  - Webhook log grid, filtered by order number and status;
  - Warnings, listing lines sent with no SKU or weight in the last 30 days.

  Grids use the nopCommerce DataTables helper, as CustomerProfile's admin lists do.

**4.50 differences** (backport step):
- block-scoped namespaces;
- `_permissionService.AuthorizeAsync(...)` checks inside actions instead of `[CheckPermission]`;
- menu through `IAdminMenuPlugin.ManageSiteMapAsync` instead of `AdminMenuCreatedEvent`;
- net6.0 csproj;
- any DataTables or `nop-card` tag-helper attribute differences (check against HandlingFee 4.50's `Configure.cshtml`).

The service layer should port unchanged. I verified that `SearchOrdersAsync`, `GetTotalNumberOfItemsCanBeAddedToShipmentAsync`, `ShipAsync(shipment, notifyCustomer)`, `FormatSkuAsync` and `ReverseBookedInventoryAsync` have the same signatures in both trees.

## Tests (NUnit, fakes, no DB, same cases in both suites)
- **Selector** rules 1–7: paid or Open Payment, PayPal pending excluded, "do not ship" auto-hold, `-EXCH` held until released, fully backordered hidden or shown by setting, combination stock, the placeholder stock values.
- **Mapper**: PO parsing ("PO# 36591" → `8102 PO 36591`), 35-character trim, `customerNotes` HTML stripping, service keys, title with the attribute description and backordered prefix, the weight fallback chain, the state abbreviation and 10-digit phone.
- **Tracking parser**: T10 input, carrier detection, stripping "UPS 1ZC…", "Hand Deliver" → no carrier.
- **Update processor**: duplicate → no-op (T9), unknown GUID → 422 with nothing created (T12), quantity capped (T13), partial-shipment sequence (T15), multi-package note without an email (T22).
- **Request guard**: HTTP → 403, bad key → 401, lockout threshold.
- **Void**: shipping status recomputed (gap #1).
